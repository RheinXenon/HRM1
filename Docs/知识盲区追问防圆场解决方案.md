# 知识盲区追问防"圆场"解决方案

## 问题描述

候选人AI在知识盲区（`actual_level` < `perceived_level`）被追问时，会倾向于"圆过去"，即：
- ❌ 说出超出能力范围的正确专业术语（如 actual_level=3 却说"依赖数组"、"Object.is"、"useCallback"）
- ❌ 给出部分正确的技术解释，而非诚实承认不懂
- ❌ 重复面试官问题中的专业术语，假装理解

这导致面试系统无法有效识别候选人的真实知识边界。

## 解决方案：Few-Shot Negative Examples（少样本负面示例）

### 核心方法

参考业界提示词工程最佳实践（PromptHub Blog）：
> "Use both positive and negative examples - the LLM can learn a lot from what a 'bad' output looks like"

在追问场景的提示词中**同时提供错误示例和正确示例**，通过具体示例引导LLM：明确标记哪些回答方式是禁止的，哪些是期望的。

### 实现方式

#### 1. 追问时动态注入对比示例

在 `agents/candidate_agent.py` 的 `answer_question` 方法中，当检测到追问时：

```python
if is_followup:
    # 针对不同 actual_level 提供具体的对比示例（通用化设计，适用所有行业）
    if level <= 3:
        # ❌ 错误示例（标记为禁止的回答方式）
        "我理解【专业概念A】的原理是通过【机制B】来实现的，其中涉及【要素C】和【要素D】..."
        → 错误！说出了具体的专业术语、原理解释、技术细节！
        
        # ✅ 正确示例（标记为期望的回答方式）
        "呃...您问的这些，说实话我不太清楚。我只是大概知道有这么个东西，但具体是怎么回事...这些我真没深入了解过"
        → 正确！完全避免专业术语，诚实承认了解不深
```

#### 2. 系统提示词中加入负面示例

在 `agents/prompts/candidate_prompts.py` 中：

```python
3. **知识盲区处理（核心机制 - 使用Negative Examples）:**
   
   * ❌ 错误示例（actual_level=3时绝不能这样回答）:
     - "我理解【专业概念】的原理是通过【机制】来实现的..."
     - "需要用到【方法A】、【方法B】和【方法C】..."
     → 这些都包含了具体的专业术语、原理解释、方法细节！
   
   * ✅ 正确示例（actual_level=3时应该这样回答）:
     - "呃...这个具体我不太清楚，只是大概知道有这么回事..."
     - "这块我了解不深，听说过但具体怎么做我真不知道"
     → 诚实承认不知道，完全避免专业术语
```

#### 3. 明确表达边界

在追问提示词中加入以下规则：

```python
**核心原则: 你的actual_level决定了你能使用的术语范围**
- 追问不会让你'突然想起'新的专业术语
- 即使面试官问题中提到某个术语，如果超出你的能力，也不要重复使用它
- 用'这个'、'那个'、'某些功能'等模糊词汇代替你不懂的专业术语
- 示例：用"那个返回的函数"代替"cleanup函数"
```

## 效果验证

### 测试用例
- **候选人配置**: React skill actual_level=3, perceived_level=7
- **追问问题**: "能具体说说依赖数组的工作原理吗？cleanup函数的执行时机是什么？"

### 对比结果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| **专业术语** | ❌ 说出"依赖数组"、"useCallback"、"cleanup" | ✅ 完全避免专业术语 |
| **技术解释** | ❌ 给出"React会对比..."等正确解释 | ✅ 仅说"不太清楚"、"没研究过" |
| **评分变化** | 下降 1-3 分 | 下降 17.5 分（52.5→35.0） |
| **露怯信号** | 少量 | 明显（"不太清楚"、"记不太清了"） |

### 实际回答示例

**❌ 修复前（会"圆过去"）:**
> "我理解依赖数组的原理是React会用Object.is进行浅比较，所以如果传对象会导致引用不同，需要用useCallback来稳定引用...cleanup函数是在组件卸载时调用的..."

**✅ 修复后（诚实露怯）:**
> "您问的这些细节我其实不太清楚。我们项目里就是照着例子写...但为什么这样能行...这些底层的原理我没太研究过。那个返回的函数什么时候执行我也记不太清了...具体的真说不上来。"

## 技术要点

1. **具体化约束**: 不使用抽象规则"不要说术语"，而是在提示词中明确列出禁止使用的具体术语示例
2. **提供替代表达**: 在示例中展示如何用模糊词汇（"这个"、"那个"、"某些方法"）替代专业术语
3. **按能力分层**: 针对不同 actual_level（1-3, 4-5, 6+）提供对应的错误/正确示例
4. **追问场景触发**: 这些约束仅在 `is_followup=True` 时添加到提示词，不影响初次回答
5. **纯提示词实现**: 不使用字符串匹配、替换或任何后处理过滤，完全通过提示词中的示例来引导LLM生成符合要求的输出
6. **领域无关设计**: 使用【专业概念】、【方法A】等占位符，避免硬编码特定行业术语，适用于技术、营销、护理、教育等所有领域
