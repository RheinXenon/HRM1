# 追问机制功能说明

## 概述

追问机制是识别"不懂装懂"候选人的关键功能。当候选人的回答得分高但内容可疑时，面试官会自动进行深入追问，通过候选人在追问环节的表现来判断其真实能力。

## 核心机制

### 1. 浅层回答检测

面试官Agent会自动检测候选人的回答是否"浮于表面"，检测信号包括：

#### 检测信号

| 信号类型 | 描述 | 触发条件 |
|---------|------|---------|
| **高级术语+缺乏细节** | 使用"微服务"、"分布式"等术语但回答< 150字 | 有高级术语且回答短 |
| **模糊词汇** | 使用"一般"、"大概"、"应该"等模糊词 | 出现≥2个模糊词 |
| **回答过短** | 回答少于80字但得分≥7 | 长度vs评分不匹配 |
| **缺乏数据** | 谈技术概念但没有任何数字/指标 | 无数字且得分≥7 |
| **缺乏示例** | 回答< 100字且没有"例如"、"具体"等词 | 缺少实例支撑 |

#### 判定逻辑

```python
# 满足以下任意组合即判定为可疑：
suspicious = (
    (高级术语 AND 回答<150字) OR
    (模糊词≥2个) OR
    (回答<80字 AND 得分≥7) OR
    (高级术语 AND 无数字 AND 得分≥7) OR
    (高级术语 AND 无示例 AND 回答<100字)
)
```

### 2. 追问问题生成

根据不同技能领域，系统内置了针对性的追问问题库：

#### System Design 架构设计
- "你提到了{concept}，能具体说说这个方案能支持多大的并发量（QPS）吗？"
- "如果让你画个架构图来说明{concept}，你会怎么画？请描述主要模块和数据流。"
- "这个{concept}设计在实际项目中遇到过什么具体问题？是怎么解决的？"
- "能否说明一下{concept}方案的trade-off？为什么选择它而不是其他方案？"

#### React 前端框架
- "你提到React的{concept}，能写一小段代码示例来说明吗？"
- "React的{concept}底层原理是什么？和其他框架有什么本质区别？"
- "如果我问你virtual DOM的diff算法时间复杂度，你知道吗？"
- "在实际项目中使用{concept}时遇到过什么性能问题？"

#### Java 后端
- "你提到{concept}，能说说JVM的具体参数配置吗？"
- "Spring的{concept}源码你看过吗？能简单说说实现原理吗？"
- "在生产环境中{concept}的监控指标你会看哪些？"

#### 微服务
- "你提到使用了{concept}，具体是用的什么中间件或框架？"
- "服务之间的数据一致性是如何保证的？能举个具体例子吗？"
- "如果一个服务挂了，整个系统会怎么处理？有什么降级策略？"

#### 性能优化
- "你提到性能优化，具体优化前后的指标是多少？"
- "这个优化方案的瓶颈分析是怎么做的？用了什么工具？"
- "如果数据量增长10倍，这个方案还能work吗？"

#### 数据库
- "你提到数据库优化，能说说具体的索引设计吗？"
- "执行计划（EXPLAIN）结果你是怎么分析的？"
- "这个查询的时间复杂度是多少？数据量多大时会成为瓶颈？"

### 3. 追问流程

```
┌─────────────────┐
│  候选人初次回答  │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  面试官评分     │ (假设得分 75.0/100)
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  检测是否可疑   │
│  - 使用高级术语  │
│  - 回答仅120字  │
│  - 无具体数据   │
└────────┬────────┘
         │
         ▼ (可疑 = True)
┌─────────────────┐
│  生成追问问题   │ 🔍
│  "能具体说说QPS │
│   是多少吗？"   │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 候选人追问回答  │
│ (如果不懂装懂，  │
│  这里会暴露)    │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 重新评估追问答案│ (假设得分 45.0/100)
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  比较前后评分   │
│  75 → 45 (下降30分)│
│  标记：🚩 不懂装懂│
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 调整最终评分    │
│ 使用追问评分45.0/100 │
└─────────────────┘
```

### 4. 评分调整策略

追问后根据分数变化采取不同策略（基于0-100标准化评分）：

| 情况 | 评分变化 | 最终评分 | 标记 |
|------|----------|----------|------|
| **暴露不懂装懂** | 下降≥20分 | 使用追问评分 | 🚩 追问后露怯 |
| **依然扎实** | 上升或持平 | 使用追问评分 | ✅ 追问后依然扎实 |
| **轻微下降** | 下降<20分 | 取平均值 | ⚡ 追问后略有下降 |

### 5. 触发条件

追问机制仅在同时满足以下条件时触发：

1. **初次评分≥60分** - 避免对低分回答浪费追问（良好水平以上）
2. **检测到可疑信号** - 至少触发一个检测信号
3. **涉及技术领域** - 针对技术问题才追问

## 效果示例

### 示例1：成功识别不懂装懂

**场景**：张强（过度自信候选人）对System Design实际能力50/100但自我感觉80/100

**初次回答**：
> "在微服务架构中，我们采用了Saga模式来保证数据一致性，通过消息队列实现最终一致性。"
> - 长度：45字
> - 标准化评分：72.0/100
> - 检测：✅ 使用高级术语但回答较短

**追问**：
> "你提到使用了Saga模式，具体是用的什么中间件或框架？"

**追问回答**：
> "这个...我们使用的是消息队列，具体的配置我记不太清楚了..."
> - 长度：30字
> - 标准化评分：38.0/100 ⬇️

**最终判定**：
- 评分：72.0 → 38.0 (下降34分)
- 标记：🚩 追问后露怯
- 结论：怀疑不懂装懂

---

### 示例2：经受住追问考验

**场景**：李明（理想候选人）真实System Design能力90/100

**初次回答**：

**结果**：未触发追问（回答已经足够详细）

## 局限性与改进方向

### 当前局限性

1. **依赖评分准确性** - 如果初次评分就很低，不会触发追问
2. **问题库固定** - 追问问题是预设的，可能不够灵活
3. **单轮追问** - 目前只追问一轮，深度不够

### 未来改进方向

1. **多轮连续追问** - 对同一话题连续深入追问2-3轮
2. **动态问题生成** - 使用LLM根据具体回答生成追问
3. **语义分析** - 分析回答的语义深度而不仅是长度
4. **知识图谱** - 建立技术知识图谱，检查回答的逻辑一致性
5. **候选人反应分析** - 分析"这个..."、"我记不太清"等心虚表达

## 总结

追问机制通过**检测 → 追问 → 对比**三步流程，有效识别候选人的不懂装懂行为。核心原理是：真正懂的人在深入追问下依然能给出详实回答，而不懂装懂的人会暴露知识漏洞。

配合知识误判功能（self_awareness + knowledge_blind_spots），系统能够：
1. 模拟候选人的不懂装懂行为
2. 识别并暴露这种行为
3. 真实反映候选人的实际能力水平

这使得自动面试系统更接近真实面试场景，为面试官培训和评估系统优化提供了有力工具。
